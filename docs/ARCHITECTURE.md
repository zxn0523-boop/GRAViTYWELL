# GravityWell 架构说明（零基础版）

## 一次对话怎样流动

1. 浏览器把用户的一句话发送给 FastAPI。
2. DeepSeek 只把这句话整理成参与者、出发地、时间、活动和偏好；模糊时段按产品固定规则补成明确时刻。
3. 程序检查是否缺信息；每轮只补问一个问题。
4. 高德同时查询地址和 POI；程序组合比较多人候选，优先同城与明确城市，再由页面要求用户确认。
5. 程序在多人坐标附近生成三个“搜索种子”。种子不是推荐结果，只用于寻找真实 POI。
6. 高德返回场所类型、地图评分、营业时间，并为每个人到每个候选计算真实路线。
7. 程序淘汰计划到达时已关闭或无法可靠解析已有营业时间的地点；已知营业时间需覆盖到达后至少一小时。
8. Python 评分器结合需求、地图口碑、交通公平、整体便利、换乘和天气排序，并执行 90 分钟、3 次换乘等硬限制；“照顾某人”会启用单独的搜索种子与评分权重。用户明确要求“在某地附近”时，该区域成为搜索中心，候选限制在 5 公里内，并将位置要求置于交通公平之前。
9. DeepSeek 只解释计算结果，不允许改动数字。
10. 用户继续调整时复用本轮状态；采纳、重开或超时后删除状态。

## 文件分别负责什么

- `app/main.py`：总入口，接收网页请求并把各模块接起来。
- `app/models.py`：数据字典，规定“参与者”“路线”“候选地点”必须有哪些字段。
- `app/services/deepseek.py`：自然语言理解与结果说明。
- `app/services/amap.py`：高德地址、POI、路线和天气接口。
- `app/services/recommender.py`：生成候选、建立多人路线矩阵。
- `app/core/scoring.py`：确定性的公平评分，是产品核心。
- `app/repositories/sessions.py`：SQLite 临时会话，负责保存和删除。
- `static/`：仅用于测试推荐逻辑的简单网页。
- `tests/`：不调用真实付费 API 的自动测试。
- `scripts/smoke_test.py`：需要真实 API 的同城/邻城人工冒烟测试。

## 为什么暂时没有 Tavily

MVP 要验证的是地图推荐是否真实、公平。地点、路线和近期天气都由高德提供，Tavily 不参与核心证据链。以后若要核实展览公告、临时闭馆或活动信息，再单独接入，避免当前系统增加成本和不确定性。

## 氛围怎样进入计算

“设计感、安静、聊天、约会”等词不只是写在推荐理由里。程序会在路线计算前降低快取咖啡连锁的优先级，过滤便利店附属、外卖和取餐档口，并提升酒店、艺术空间、书店、庭院等更可能适合停留的 POI。这个判断仍受高德 POI 信息完整度限制，因此最终应由用户确认场所实际状态。

主场所类型不会被氛围覆盖：明确要求咖啡馆时，只在不同氛围的咖啡馆中选择；明确提出散步、夜景、逛街、看展等活动时，才扩展到公园、绿道、街区、广场或文化场所。地图服务内部仍把这些地理对象统称为 POI，但产品会按场所、公园、街区和景点分别展示。

## 当前数据边界

- `api.env` 只由后端读取，网页拿不到密钥。
- SQLite 只保存未完成会话。
- 点击采纳或重新开始会立即删除本轮状态。
- 每次读取会话前都会清理超过 24 小时的记录。
- 当前不建立账号、不保存用户画像、不做长期位置记忆。

## 模糊时间的固定默认值

为保证路线、营业时间和天气能够计算，用户只给时段时不再补问具体几点：凌晨 01:00、早上 09:00、上午 10:00、中午 12:00、下午 14:00、傍晚 18:00、晚上 19:00、夜间 20:00。用户给出明确时刻时始终以用户输入为准。
